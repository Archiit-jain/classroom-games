# ADR-014: Lenient action versions + unique action ids

**Status:** Accepted (product owner, Phase 2). Replaces the strict reading of spec §15.

## Context

Spec §15 says every action carries `{matchId, version}` and a stale action is rejected with
`STALE_VERSION` "so double-taps are harmless". Implemented literally (reject unless
`version === current`), this breaks simultaneous play: in 16 Parchi, when player A selects a
chit the version increases, so player B's selection — sent a moment earlier from the
previous view — would be rejected and B would have to tap again. The claim race would also
turn the second valid claim into `STALE_VERSION` instead of giving it the next placement.

Versions alone also cannot stop a replayed or duplicated message from executing twice.

## Decision

1. **Versions are lenient.** The server rejects only versions it never issued
   (`version > current`) with `STALE_VERSION`. Older, previously issued versions are
   accepted; **legality is always decided by the engine against the current state**.
2. **Every client game action carries a unique `actionId`** (8–64 URL-safe characters,
   generated by the client once per intent). The runtime processes each id **at most once
   per match**: a repeat is rejected with `DUPLICATE_ACTION`, whatever happened to the first
   attempt (accepted or illegal). A future/unknown version is rejected _before_ the id is
   recorded, so it does not burn the id. Ids are remembered per match (bounded at 10,000).
3. **Clients coalesce double taps:** an identical action still waiting for its
   acknowledgement is not sent again (`apps/client/src/platform/actions.ts`). The UI treats
   `DUPLICATE_ACTION` silently.
4. Bots (server-side) submit without a version or id.
5. On the client, a version gap does not trigger a resync request: every update carries a
   complete view, so a gap only means skipped animations. `match:resync` exists for explicit
   refreshes.

## Consequences

- Simultaneous games and races behave naturally; double taps and replays cannot execute
  twice.
- Engines must validate against state, never trust that the client saw the latest view
  (they already must, for security).
- Tests: duplicate action, two players acting on the same slightly old version, a
  stale-but-valid action, future/unknown versions, replay of an earlier id (runtime unit
  tests with a simultaneous test game, plus socket-level tests).
